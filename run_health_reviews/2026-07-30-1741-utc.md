**Root cause (read-only diagnosis, no source touched):** `market_data.py:get_price()` (~line 155-160) has two branches. The `len(history) == 1` branch already guards against a zero denominator (`if curr["open"] else 0`), but the `len(history) >= 2` branch does not guard `prev["close"]`:
```python
if len(history) >= 2:
    prev, curr = history[-2], history[-1]
    change_pct = round(((curr["close"] - prev["close"]) / prev["close"]) * 100, 2)  # <-- no zero-guard
elif len(history) == 1:
    curr = history[0]
    change_pct = round(((curr["close"] - curr["open"]) / curr["open"]) * 100, 2) if curr["open"] else 0
```
Some ticker in today's fetch loop is returning a 2-bar history whose second-to-last bar has `close == 0` (a data glitch or a frozen/halted-ticker artifact, same general family as the delisted-ticker issue fixed yesterday in `1f96273`, but a different code path — that fix touched `get_extended_history`'s dead-history guard, not `get_price`). This is **not the same bug** as yesterday's `is_history_dead()` fix; it's a fresh gap in a sibling function the fix didn't cover. The exception is unhandled at the call site (`get_market_snapshot`, line 788) and kills the entire fetch job — one bad ticker takes down the whole day's snapshot.

**Minimal repro idea for the fix session:** call `get_price()` with a synthetic 2-bar history where `history[-2]["close"] == 0`; assert it returns a snapshot with `change_pct` degraded (e.g. `0` or `None`) instead of raising. Mirror the existing guard style already used in the `len==1` branch.
